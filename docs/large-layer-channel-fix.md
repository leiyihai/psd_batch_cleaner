# 修复真实项目唯一拒绝：区分记录预算与像素通道载荷

## 症状、反馈环和根因

146文件的真实CLI测试中，`英雄页V3.psd`被拒绝为“图层记录区超过128 MiB校验上限”。原稿只读，历史批次的报告和145份输出保持不变；本次没有重跑整个项目。

最初单文件反馈命令为本地诊断脚本：

```powershell
$env:PYTHONPATH='.'
.\.venv\Scripts\python.exe -X utf8 .prototype-data/tools/reproduce_hero_layer_limit.py
```

修复前连续两次返回RED，分别约2.29/2.18秒，错误与真实批次完全相同。随后用一个图层、3个RAW通道的结构自洽夹具最小化：缩小通道时通过，仅把通道载荷增加到略超128 MiB就复现同样拒绝，无需原稿的7099个记录、智能对象或大XMP；原稿没有被裁剪或改写。最小大通道反馈环修复后约0.045秒返回GREEN。

在测试前提出并排序的假设为：整个LayerInfo被误当作记录预算、真正记录元数据超限、长度/通道framing损坏。真实只读测量证据`.prototype-data/hero-layer-limit/measured-records.json`区分了它们：

| 项目 | 字节 |
| --- | ---: |
| 整个LayerInfo | 281,154,072（268.13 MiB） |
| 记录元数据 | 27,462,602 |
| 紧凑通道长度索引 | 227,416 |
| 像素通道载荷 | 253,691,467 |
| 尾部填充 | 3 |

共有7099个**记录**（不等于7099个实际可编辑图层节点）、28427个通道，最大的单个记录16110字节；RAW/RLE头和长度边界自洽。根因是将包含像素通道的整个LayerInfo套入了记录校验预算，不是文件必须突破记录预算，也不是已证明的源文件损坏。

## 修复，不提高预算

`Planner`继续调用psd-tools解析每条LayerRecord，但不再使用会整体物化外层ChannelImageData的LayerInfo/LayerInfoBlock读取路径；记录额外标签仍按库解析，计入记录预算。

- **记录元数据＋紧凑通道长度索引合计仍限128 MiB**。记录读取窗口在实际分配前受预算约束；使用固定宽度整数索引，不保留全部记录对象或通道载荷。
- 分别处理PSD/PSB普通LayerInfo的长度前缀，以及没有内层前缀的Lr16/Lr32。
- 逐通道验证长度、范围及压缩枚举，零长度合法、一字节长度拒绝；通道数据按原区间分块复制并比较，不解压/重新编码。
- 恢复并保留原LayerInfoBlock的parse_context/parse_container保护，不能在替换读取器时丢失嵌套和对象预算。新增低嵌套预算回归先暴露了此遗漏，再修正通过。
- 未改变尾部opaque填充保留、Layr拒绝、合成图解压128 MiB、XMP128 MiB、替换数据256 MiB、嵌入深度或文档数等既有规则。
- 未修改像素、组层级、智能对象标识或其他元数据。清理规则身份更新为`ancestors-file-patches-v4-stream-layer-records-psdtools-1.26.1`，旧缓存下次需重新验证；已打开的GUI需重启才能使用新代码。

128 MiB是解析数据预算，不是整个Python进程工作集的保证。新旧路径都没有对每层通道执行像素解压验证；压缩头/范围校验不能冒充Photoshop编辑及视觉验收。选择理由及代价同步到[区间补丁ADR](adr/0001-stream-metadata-patches.md)。
